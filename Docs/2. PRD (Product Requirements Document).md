## 1. Executive Summary

This document defines the product requirements for a multi-role **Real Estate Management & Property Discovery Platform** — a SaaS-style application connecting **Builders**, **Brokers**, and **Buyers** through a single system, with an **Admin** layer for governance.

Unlike a typical "property listing app," this platform combines property discovery, lead/booking management, analytics, and location intelligence (maps, nearby infrastructure) into one product — and covers both **Sale and Rental listings in a single marketplace**. The goal is to make it a portfolio-grade, production-style system that demonstrates full-stack engineering, RBAC design, cloud deployment, DevOps practices, and applied AI — not just CRUD screens.

---

## 2. Problem Statement

Property discovery in India today is fragmented across three broken experiences:

| Stakeholder | Current Pain Point |
|---|---|
| **Buyer** | Has to browse multiple sites, can't easily compare properties, doesn't know EMI affordability or locality quality (schools/metro/hospitals) upfront. |
| **Broker** | Manages leads manually (WhatsApp/Excel), no structured way to track visits, enquiries, or conversions. |
| **Builder** | No visibility into which listings perform well, no analytics on views vs bookings, manual approval/verification process. |
| **Admin/Platform** | No centralized way to verify listings, prevent fake properties, or track platform health. |

**Goal:** Build one platform where each role gets a purpose-built workflow, backed by a shared property database, RBAC-controlled access, and real analytics.

```

       ┌──────────────┼──────────────┐
       │              │              │
   Builder          Broker         Buyer
```

### 4.1 Admin
**Purpose:** Platform governance and quality control.
- Manage all users (builders, brokers, buyers)
- Approve / reject property listings before they go live
- Delete fake or duplicate listings
- View platform-wide analytics (traffic, revenue, growth)
- Manage broker/builder accounts (suspend, verify)

### 4.2 Builder
**Purpose:** List and manage real estate projects/units.
- Add / edit / delete properties
- Upload property images and floor plans
- View bookings made against their properties
- View property-level analytics (views, wishlist count, conversion)

### 4.3 Broker
**Purpose:** Manage client-facing sales pipeline.
- List properties (on behalf of builders or independently)
- Schedule and manage property visits
- Contact and track buyer leads
- Manage lead pipeline (new → contacted → visit scheduled → closed)

### 4.4 Buyer
**Purpose:** Discover and evaluate properties.
- Search and filter properties
- Save to wishlist
- Compare multiple properties side-by-side
- Book property visits
- Contact builder/broker directly

### Authentication Flow

**Standard (Email/Phone):**
```
Register → Email/Phone Verify → Login → JWT Issued → Role Claim Embedded → Protected API Access
```

**OAuth2 (Google Login):**
```
"Continue with Google" → Google OAuth2 Consent Screen → Callback with Auth Code
→ Backend Exchanges Code for Google Profile → Match/Create User Record
→ JWT Issued (same shape as standard login) → Role Claim Embedded → Protected API Access
```
- On first-time Google login, user is created with a default `Buyer` role (role upgrade to Broker/Builder requires separate verification, not self-selectable via OAuth)
- Google account email is used to de-duplicate against existing email/phone-registered accounts
- JWT-based stateless authentication
- Role embedded in JWT payload, validated via RBAC middleware on every protected route
- Refresh token rotation for session longevity without re-login

## 5. Functional Requirements (Modules)

Each module below includes: **purpose, features, and acceptance criteria** — the format interviewers and reviewers expect from a real PRD.

### 5.1 Dashboard (Role-Specific)

**Purpose:** Give every role a home screen relevant to their workflow, not a generic landing page.

| Role | Dashboard Widgets |
|---|---|
| Buyer | Saved Properties, Recently Viewed (last 20), Similar Properties, Recommended Properties, Upcoming Visits, Wishlist, Search History |
| Broker | Total Listings, Today's Leads, Upcoming Visits, Sold Properties, Customer Enquiries, Revenue |
| Builder | Projects, Units Available, Bookings, Revenue, Property Analytics, Pending Approvals |
| Admin | Users, Builders, Brokers, Properties, Site Traffic, Revenue, Reports, Analytics |

**Recently Viewed — Detail:**
- Shows the buyer's **last 20 viewed properties**, most recent first
- Backed by a capped log (`recently_viewed` table or Redis list per user, trimmed to 20 entries via `LTRIM`/rolling delete) — avoids unbounded growth per user
- Deduplicated: re-viewing a property moves it to the top rather than adding a duplicate entry

**Similar Properties — Detail:**
- Auto-surfaced on the buyer dashboard and property detail page, based on the buyer's own **past search/view history** (city, budget range, BHK, property type patterns)
- V1 approach: rule-based similarity — match on same city + overlapping budget range (±10%) + same bedroom count as the buyer's most frequent search pattern
- V2 (future, ties into AI-infra interest): swap rule-based matching for a lightweight recommendation model using view/wishlist/search embeddings

**Acceptance Criteria:**
- Dashboard loads role-appropriate data only (enforced server-side, not just UI-hidden)
- Data is paginated/cached — no full-table dumps on dashboard load
- Recently Viewed list never exceeds 20 entries per user
- Similar Properties never suggests a property the buyer has already booked/rejected

### 5.2 Property Management

**Purpose:** Core CRUD + approval workflow for listings.

**Listing Type (Scope Expansion — Rental + Buy in One Platform):**
- Every property carries a `Listing_Type` field: `Sale` or `Rent`
- Rental listings carry additional fields: `Monthly_Rent`, `Security_Deposit`, `Lease_Duration`, `Furnishing_Status`
- Search, filters, and Finance Suite (Section 5.4) adapt based on `Listing_Type` — e.g., EMI Calculator shows for Sale, Rent Affordability view shows for Rent
- This makes the platform a combined **Rental + Buy Marketplace** rather than a sale-only portal, matching how real Indian portals (99acres, MagicBricks) operate

**Property Entity Fields:**
```
Title, Description, Price, Listing_Type (Sale/Rent), Area, Bedrooms, Bathrooms, Parking,
Builder (FK), Property Type, Amenities, Status, Latitude, Longitude, Images
```

**Draft → Publish Workflow:**
- Builder/Broker can save a listing as `draft` at any point — incomplete fields allowed, not visible anywhere publicly
- Draft can be resumed and edited any number of times before submission
- Explicit "Publish" action moves it from `draft → pending` (enters admin approval queue)
- Drafts auto-saved every 30s while editing (prevents data loss on accidental navigation)

**Features:**
- Add / Update / Delete property (Builder/Broker scoped to own listings)
- Save as Draft / Publish Later
- Admin Approve / Reject workflow — properties are `pending` until admin approval, then `live`
- Status lifecycle: `draft → pending → approved/rejected → live → sold/rented/archived`

**Content Moderation (Admin-Facing):**
- On reject, admin must select a reason: `Spam`, `Duplicate Listing`, `Fake/Fraudulent`, `Incomplete Information`, `Policy Violation`, `Other`
- Rejected listings notify the builder/broker with the reason, and remain editable → re-submittable
- Duplicate detection assist: system flags potential duplicates by matching address/lat-long + price + area similarity before admin review (reduces manual duplicate-hunting)
- Repeated fake/fraudulent submissions from the same account feed into the User Verification module (Section 5.15) for account-level action

**Acceptance Criteria:**
- A property cannot appear in public search until status = `approved`
- Only the owning builder/broker or admin can edit/delete a listing (enforced at API layer)
- A rejected listing always carries a moderation reason — rejection without a reason is not allowed

### 5.4 Finance Suite (Buyer Tools)

**Purpose:** Keep every financial decision on-platform — a major reason buyers currently bounce to other sites/apps mid-journey. This is one of the strongest differentiators since most competing portals only offer a bare EMI calculator.

**5.4.1 Loan / EMI Calculator**
- **Input:** Price, Loan Amount, Interest Rate, Tenure (Years)
- **Output:** Monthly EMI, Total Interest, Total Cost, Amortization breakdown (principal vs interest over time)
```
Price: ₹80,00,000 → EMI: ₹58,000/month (example output)
```

**5.4.2 Registration Cost Calculator**
- **Input:** Property value, State (rates vary by state in India)
- **Output:** Estimated registration fee (typically ~1% of property value, state-dependent)

**5.4.3 Stamp Duty Calculator**
- **Input:** Property value, State, Buyer category (e.g., some states offer lower rates for women buyers)
- **Output:** Estimated stamp duty amount, based on a maintained state-wise rate table

**5.4.4 GST Calculator**
- **Input:** Property value, Under-Construction vs Ready-to-Move status (GST applies only to under-construction properties in India), Affordable Housing eligibility
- **Output:** Estimated GST payable

**5.4.5 Maintenance Cost Estimator**
- **Input:** Area (sqft), Property Type, City-tier
- **Output:** Estimated monthly/annual maintenance cost range, based on typical per-sqft society maintenance rates

**Technical Notes:**
- All calculators are pure client-side computation (standard formulas) — no API round-trip needed, keeps them instant
- State-wise rate tables (stamp duty, registration) stored as a seeded/configurable dataset in the DB (`Finance_Rates` table) rather than hardcoded — so rates can be updated without a redeploy
- Calculator usage optionally logged to Search History for personalized recommendations later
- For Rental listings (Section 5.2), this section adapts to show a "Rent Affordability" view instead of EMI/registration/stamp-duty (which don't apply to renting)

**Acceptance Criteria:**
- All five calculators are accessible from the property detail page without leaving the platform
- Rate tables are configurable by admin (not hardcoded in frontend), so a state's stamp duty rate can be corrected without a code change

### 5.8 Sales & Property Analytics (Builder-Facing)

**Purpose:** Give builders data to understand listing performance — beyond raw numbers, as visual trend charts a builder can act on.

**Metrics Tracked:**
```
Views, Clicks, Wishlist Count, Contact Requests, Bookings, Conversion Rate, Revenue
```

**Example:**
```
Views: 2400 → Wishlist: 420 → Visits: 53 → Bookings: 9
```

**Sales Analytics — Graphs (Builder Dashboard):**
- **Views over time** (line chart, daily/weekly/monthly toggle)
- **Leads over time** (new leads generated per period)
- **Conversion funnel** (Views → Wishlist → Visit → Booking, funnel chart)
- **Revenue over time** (line/bar chart, per project and aggregated)
- Built with Recharts on the frontend, fed by aggregated backend endpoints (not raw event data — see Technical Notes)

**Technical Notes:**
- Views/clicks tracked via an event log table (`property_views`), aggregated periodically (not real-time counted on every request, to avoid write amplification)
- Conversion rate = Bookings / Views, computed on read
- Chart endpoints return pre-aggregated time-bucketed data (e.g., `GROUP BY date_trunc('day', created_at)`), not raw rows — keeps chart rendering fast even with large event volumes

### 5.9 Property Reviews & Ratings

**Purpose:** Build trust in listings via verified buyer feedback — a major gap in current property portals where reviews are absent or unverifiable.

**Features:**
- Buyers can leave a star rating (1-5) + written review on a property
- **Verified Visit requirement:** review submission is only enabled for buyers whose booking status = `Completed` for that property (prevents fake/competitor reviews)
- Builder/Broker can publicly respond to a review (one reply per review)
- Admin can moderate/remove reviews that violate content guidelines (abuse, spam)
- Average rating displayed on property card and detail page

**Review Entity:**
```
Reviewer (FK: Buyer), Property (FK), Rating (1-5), Comment, Booking (FK, for verification), Status, Builder_Reply
```

**Acceptance Criteria:**
- A buyer can only review a property tied to a `Completed` booking of theirs (one review per booking)
- Average rating recalculates on new review submission (cached, not recomputed on every page load)
- Flagged/removed reviews are excluded from the average rating calculation

### 5.10 Lead Management (Broker/Builder)

**Purpose:** Give brokers/builders a structured sales pipeline instead of tracking leads manually on WhatsApp/Excel (the exact pain point named in Section 2).

**Lead Pipeline Stages:**
```
New Lead → Interested → Site Visit → Negotiation → Booked
```
(with a parallel `Lost/Dropped` state reachable from any stage)

**Features:**
- Every buyer enquiry (contact request, visit booking, wishlist-based interest) auto-creates or updates a Lead record
- Broker/Builder can manually move a lead through pipeline stages (drag-and-drop Kanban-style board on the dashboard)
- Each lead stores: buyer contact info, associated property, current stage, stage history (timestamps), notes, assigned broker
- Filter/sort leads by stage, property, date, or assigned broker (for builder teams with multiple brokers)

**Lead Entity:**
```
Lead_ID, Buyer (FK), Property (FK), Broker/Builder (FK), Stage, Stage_History (JSON/log), Notes, Created_At, Updated_At
```

**Technical Notes:**
- Stage transitions are logged (not overwritten) in a `lead_stage_history` table — enables the "Conversion Funnel" chart in Section 5.8 to be computed from real stage-transition data
- A lead auto-advances from `New Lead → Interested` when the buyer books a visit; further stage moves (`Site Visit → Negotiation → Booked`) are manual, broker-driven

**Acceptance Criteria:**
- A lead cannot skip directly from `New Lead` to `Booked` without passing through intermediate stages (enforced state machine, prevents data corruption)
- Every stage change is timestamped and attributed to the broker/builder who made it

### 5.11 Contact Builder / Schedule Visit

**Purpose:** Convert interest into a scheduled action.

**Flow:**
```
Select Property → Choose Date → Choose Time (within Builder/Broker Availability) → Submit Request → Builder/Broker Notified (Email + SMS)
```

**Booking Features:**
- **Date & Time selection** constrained to a **Broker Availability Calendar** — buyer can only pick slots the broker/builder has marked as open (prevents double-booking and no-show scheduling conflicts)
- **Cancel Visit** — either party can cancel; cancellation reason optional, notifies the other party
- **Reschedule Visit** — buyer or broker can propose a new date/time against the same availability calendar; original slot is freed back into availability once confirmed
- Broker/Builder manages their own **Availability Calendar** (open slots, blocked-out dates) from their dashboard — this calendar is the single source of truth for what buyers can even select

**Notification Delivery (Open-Source, Non-Paid):**
- **Email:** Self-hosted via Nodemailer + SMTP (e.g., your own domain's SMTP, or a free-tier SMTP relay) — no paid service like SendGrid required
- **SMS:** Open-source/self-hosted gateway options — e.g., routing through an Android-based SMS gateway app (SMS Gateway for Android, self-hosted) or a free-tier provider during dev/demo; avoid paid SMS APIs (Twilio, MSG91) for the portfolio build
- In-app notification (stored in `Notifications` table) remains the primary, guaranteed channel; Email/SMS are best-effort supplementary alerts

**Booking Entity:**
```
Buyer (FK), Property (FK), Broker/Builder (FK), Date, Time, Status, Rescheduled_From (nullable FK to prior booking)
```

**Status Lifecycle:** `Pending → Approved → Rejected/Cancelled/Rescheduled/Completed`

**Acceptance Criteria:**
- Buyer cannot select a date/time slot outside the broker/builder's declared availability
- Builder/broker receives a notification (in-app, extendable to email/SMS) on new booking requests, cancellations, and reschedule proposals
- Buyer sees status updates (including reschedule confirmations) on their dashboard in real time

### 5.12 Property Images & Gallery

**Purpose:** Visual-first property browsing.

**Categories:** Living Room, Bedroom, Kitchen, Balcony, Bathroom, Exterior, Floor Plan

**Gallery Features:** Slider, Zoom, Fullscreen view
**Future Enhancement:** 360° virtual tour

**Automatic Image Compression:**
- Every uploaded image is automatically optimized on upload — no manual compression step for builders/brokers
- Pipeline: Multer receives upload → Sharp resizes to multiple resolutions (thumbnail, card-view, full-detail) and compresses (WebP conversion with quality tuning) → optimized versions pushed to MinIO (self-hosted S3-compatible storage) → served via CDN or reverse-proxy caching in front of MinIO
- This keeps page-load fast regardless of what resolution/file-size the builder originally uploads, and controls storage cost

**Acceptance Criteria:**
- No raw/unoptimized image is ever served to the frontend — only the Sharp-processed, CDN-delivered versions
- Upload pipeline rejects files above a defined max size/type before processing (validation, not silent failure)

### 5.15 Admin — User Verification

**Purpose:** Prevent unverified/fraudulent accounts from operating as Builders or Brokers — directly addresses the "no centralized way to verify listings" pain point in Section 2.

**Features:**
- New Builder/Broker signups start in a `Pending_Verification` state — they can prepare draft listings but **cannot publish** until verified
- Admin reviews submitted credentials (business name, RERA registration for builders, broker license where applicable, contact proof) and marks account as `Verified` or `Rejected`
- Verified badge displayed on the builder/broker's public profile and listings (buyer trust signal)
- Admin can revoke verification at any time (e.g., after repeated content-moderation violations from Section 5.2), which immediately unpublishes that account's live listings

**User Entity (Verification Fields):**
```
Verification_Status (Pending/Verified/Rejected), Verification_Documents, Verified_At, Verified_By (Admin FK)
```

**Acceptance Criteria:**
- A Builder/Broker account cannot have any listing reach `live` status while `Verification_Status != Verified`
- Verification status change is logged with which admin performed it and when (audit trail)

### 5.16 Admin — Platform Analytics Dashboard

**Purpose:** Give the admin a bird's-eye view of platform health, growth, and activity — beyond individual property performance (which is covered in Section 5.8).

**Dashboard Charts:**
```
Daily Active Users        Monthly Revenue         Top Cities (by listings/searches)
Top Builders (by volume)  Bookings (trend)         Most Viewed Property
Top Builder (by revenue)  Top City (by revenue)    Monthly Booking Trend
```

**Acceptance Criteria:**
- Admin dashboard load time stays fast regardless of total platform data volume, because charts read pre-aggregated data, not raw event tables
- Each chart supports a date-range filter (last 7/30/90 days, custom range)

### 5.17 Property Sharing (Multi-Platform)

**Purpose:** Let buyers share a specific listing outside the platform without needing the recipient to have an account — reduces friction in word-of-mouth/family-decision-making, which is common in Indian property buying.

**Features:**
- Every property detail page has a "Share" action generating a public, unauthenticated-viewable URL
- Native share sheet integration (Web Share API) for one-tap sharing to WhatsApp, SMS, Email, or copy-link
- Shared link opens a read-only property view (no login required to view; login prompted only for wishlist/booking actions)
- Optional Open Graph meta tags on the shared URL so WhatsApp/social previews show the property image, price, and title (not just a bare link)

**Acceptance Criteria:**
- A shared property link is viewable by someone with no account on the platform
- Shared link preview (OG tags) renders correctly when pasted into WhatsApp/Twitter/LinkedIn

## 7. Technical Architecture

```
                          React + Vite (JavaScript)
                                    │
              ┌─────────────────────┼─────────────────────┐
              │                     │                     │
        Authentication         Property Module        Analytics UI
              │                     │                     │
              ├──────────┬──────────┼──────────┬──────────┤
              │          │          │          │          │
          Booking    Wishlist    Compare     Search     Maps
              │          │          │          │          │
              └──────────┴──────────┼──────────┴──────────┘
                                    │
                          Express.js API (JavaScript)
                                    │
                    RBAC Middleware + JWT Validation
                                    │
              ┌─────────────────────┼─────────────────────┐
              │                     │                     │
         PostgreSQL              Redis              File Storage
        (Prisma ORM)          (Cache/Session)      (MinIO - S3 compatible)
              │                     │                     │
              └─────────────────────┼─────────────────────┘
                                    │
                    OpenStreetMap + Overpass API (Maps/Locality)
                                    │
                              Self-Hosted / Cloud VM (Docker + MinIO)
```

### 7.1 Request Flow — Example: Buyer Searches Properties

```
1. Buyer applies filters (city, budget, BHK) on frontend
2. React sends GET /api/properties/search?city=Noida&budget=8000000&bhk=3
3. Express route hits RBAC middleware → validates JWT → confirms buyer role
4. Controller checks Redis cache for this exact filter combination
   ├── Cache HIT  → return cached JSON (fast path)
   └── Cache MISS → query PostgreSQL via Prisma (indexed columns) 
                     → cache result in Redis (TTL ~5 min)
                     → return JSON
5. Frontend renders property cards + triggers a "view" event log (async, non-blocking)
```

### 7.2 Request Flow — Example: Builder Adds a Property

```
1. Builder submits property form (with images) 
2. Images uploaded via Multer → processed by Sharp (resize/compress) 
   → pushed to MinIO → CDN/proxy-cached URLs returned
3. Property record created in PostgreSQL with status = "pending"
4. Admin dashboard surfaces it under "Pending Approvals"
5. Admin approves → status = "approved" → property becomes searchable
6. Cache invalidation triggered for relevant search-filter cache keys
```
