## 1. Purpose & Scope

This document defines the *experience layer* of the platform: who it's designed for, how they move through it, what every screen contains, what it looks like, and how it behaves when things are loading, empty, or broken. Where the FRD specifies backend behavior, this document specifies what the person actually sees and touches.

**Design direction, stated up front:** This is a trust-and-decision product, not a browsing/entertainment product — people are evaluating the second-largest purchase of their life, or trying to close a deal. The design leans toward **calm, structured, and legible** over trendy. The signature visual idea is a **blueprint/floor-plan motif** used sparingly (thin architectural line-work, grid references) — a nod to the subject matter (property, construction, planning) without becoming a literal illustration cliché.

## 3. User Flow

The full cross-role flow is diagrammed in Figma ("Real Estate Platform — Colorful Complete App Workflow"). Summarized here as the four entry-to-outcome paths this UI must support:

```
Guest  → Search (no login) → Property Detail (no login) → Finance Suite (no login)
       → [ any deeper action ] → Login Prompt → Register/Login → resumes original action

Buyer  → Login → Dashboard → Search/Filter → Property Detail
       → Wishlist / Compare / Finance Suite / Nearby Map → Schedule Visit
       → Booking Pending → Approved → Completed → Review

Broker/Builder → Login → Verification gate (if pending) → Dashboard
       → Create/Publish Property → Admin Review → Live
       → Lead Board (New → Interested → Site Visit → Negotiation → Booked)
       → Sales Analytics

Admin  → Login → Dashboard → Verification Queue / Moderation Queue
       → Platform Analytics
```

**UX principle carried from this flow:** the Guest path is a first-class path, not a stripped-down fallback — Priya (the Buyer persona) should be able to do real evaluation work (search, view, calculate EMI) before ever hitting a login wall. The login wall appears only at the point of *commitment* (wishlist, booking, review), and always resumes the action that triggered it — the person should never have to re-find what they were doing after logging in.

## 7. UI Requirements

| ID | Requirement |
|---|---|
| UI-REQ-01 | Every destructive action (delete listing, reject verification, cancel booking) requires a confirmation step — never a single click with no undo path. |
| UI-REQ-02 | Every form persists in-progress input on accidental navigation away, where the underlying data supports it (Property Editor drafts per FR-PROP-02; login/search forms do not need this). |
| UI-REQ-03 | Search filters are reflected in the URL query string so results are shareable/bookmarkable. |
| UI-REQ-04 | The login wall, when triggered mid-action (wishlist, booking, review), resumes the original action immediately after successful login — never drops the person back at a generic dashboard. |
| UI-REQ-05 | All primary actions (Schedule Visit, Publish Property, Approve/Reject) are reachable within 2 taps/clicks from the relevant screen — no primary action buried in a submenu. |
| UI-REQ-06 | Multi-step forms (Property Editor) show a persistent step indicator and allow jumping back to a prior step without losing later-step data. |
| UI-REQ-07 | Every async action (submit, approve, book) shows immediate feedback (button loading state) — no silent waits with no visual acknowledgment. |
| UI-REQ-08 | Currency values are always shown in Indian numbering format (₹85,00,000, not ₹8,500,000) throughout. |

## 8. Design System

### 8.1 Color Palette

The direction: a grounded, professional "architectural blueprint" feel — deep ink blue for structure and trust, warm gold used sparingly for commitment-moment actions (book, publish, approve), not decoration. Deliberately not the cream+terracotta or dark+neon defaults — real estate decisions are made in daylight, on spreadsheets, with family present; the palette should feel like it belongs in that room. Dark theme exists as a secondary, equally-considered mode (not an auto-inverted afterthought) for late-evening browsing — Priya's persona data shows heavy mobile use, and evening is a realistic browsing window.

**Base/semantic tokens (theme-agnostic names, values swap per theme):**

| Token | Role |
|---|---|
| `--bg` | Page background |
| `--surface` | Card/panel background |
| `--border` | Dividers, card borders |
| `--text-primary` | Headings, primary body text |
| `--text-secondary` | Secondary/meta text, icons |
| `--action-primary` | Primary buttons, links, active states |
| `--action-primary-hover` | Hover/pressed state of primary actions |
| `--accent-cta` | High-commitment CTAs only (Schedule Visit, Publish, Approve) |
| `--success` | Approved, Verified, Completed states |
| `--warning` | Pending states, moderation flags |
| `--danger` | Rejected, errors, destructive actions |

**Light theme (default):**

| Token | Hex | Notes |
|---|---|---|
| `--bg` | `#F7F5F1` (stone-50) | Warm off-white, not stark white |
| `--surface` | `#FFFFFF` | Cards sit one step lighter than the page |
| `--border` | `#E7E3DA` (stone-200) | |
| `--text-primary` | `#101B33` (ink-900) | |
| `--text-secondary` | `#243759` (ink-700) | |
| `--action-primary` | `#2F5CA6` (blueprint-500) | |
| `--action-primary-hover` | `#24487F` | Darkened blueprint |
| `--accent-cta` | `#C9962E` (gold-500) | White text on top, always contrast-checked |
| `--success` | `#2E8B57` | |
| `--warning` | `#B8860B` | |
| `--danger` | `#C1432A` | |

**Dark theme:**

| Token | Hex | Notes |
|---|---|---|
| `--bg` | `#0B1220` | Near-black navy, not pure black — keeps the "ink" identity rather than going generic dark-mode gray |
| `--surface` | `#141D33` | One step lighter than `--bg`, gives cards visible separation without a hard border everywhere |
| `--border` | `#26314D` | |
| `--text-primary` | `#EDEFF5` | Off-white, not pure white (reduces glare on OLED/at night) |
| `--text-secondary` | `#A9B2C8` | |
| `--action-primary` | `#6C93D6` | Lightened blueprint — the light-theme blueprint-500 fails contrast on a dark background, so this is a distinct value, not just an opacity tweak |
| `--action-primary-hover` | `#8AA9E0` | |
| `--accent-cta` | `#E0B255` | Lightened/more saturated gold for AA contrast on dark surfaces |
| `--success` | `#4FAE7C` | |
| `--warning` | `#D9A441` | |
| `--danger` | `#E2695A` | |

**Implementation note:** both themes are defined as CSS custom properties at the root (`:root` for light, `[data-theme="dark"]` or `.dark` class for dark), consumed by Tailwind via `theme.extend.colors` referencing `var(--token)` — components never hardcode a hex value, only ever the semantic token, so the same component renders correctly in both themes with zero per-component logic. Theme preference follows system (`prefers-color-scheme`) by default, with a manual toggle in Profile & Settings (S-23) that overrides and persists.

**Accessibility carry-over:** every pairing above must independently satisfy A11Y-01 (Section 12) in its own theme — a token swap for dark mode is not allowed to silently drop below 4.5:1 contrast; each dark-theme value listed here was chosen specifically to hold that ratio against its paired `--bg`/`--surface`, not derived by mechanically inverting the light value.

### 8.2 Typography

| Role | Typeface | Notes |
|---|---|---|
| Display / Headings | **Sora** (geometric, structured — reads as "architectural," pairs with the blueprint concept without being literal) | Used with restraint — page titles and section headers only, not body copy |
| Body / UI | **Inter** | Highly legible at small sizes, essential for dense dashboards/tables (Arjun's and Rakesh's personas live in tables) |
| Numeric / Data | **Inter** (tabular figures enabled) | For EMI numbers, analytics — tabular figures keep columns of numbers aligned |

**Type scale:** `text-xs` (12px, captions/meta) → `text-sm` (14px, body/table) → `text-base` (16px, default body) → `text-lg` (18px, card titles) → `text-2xl` (24px, section headers) → `text-4xl` (36px, page-level headers, used sparingly)

### 8.3 Spacing & Layout

- Base unit: 4px (Tailwind default scale) — all spacing in multiples of 4
- Content max-width: 1280px on desktop, full-bleed on mobile with 16px side padding
- Card border-radius: 8px (structured, not overly soft — matches the "blueprint" restraint)
- Elevation: two levels only — `shadow-sm` (resting cards) and `shadow-md` (modals, dropdowns); avoid deep/dramatic shadows, which read as decorative rather than functional here

### 8.4 Iconography

- Icon set: **Lucide** (matches the established React stack, `lucide-react` is already an available library)
- Icons are always paired with a text label in navigation (never icon-only nav, for clarity across Meera's lower tech-comfort persona)
- Status icons (verified ✓, pending ⏱, rejected ✗) use consistent shapes across the entire platform — a "pending" icon looks the same whether it's a booking, a lead, or a verification

## 10. Responsive Rules

| Breakpoint | Width | Layout Behavior |
|---|---|---|
| Mobile | < 640px | Single column. Filter panel becomes a bottom `Sheet`. Kanban board becomes a stage-selector dropdown + single-column card list (drag-and-drop replaced with a "Move to..." menu action — dragging doesn't work well on touch for this pattern). Property Detail sections stack fully. |
| Tablet | 640px – 1024px | Two-column where content allows (property grid: 2 cards/row). Sidebar filters become collapsible, not a full sheet. Kanban board scrolls horizontally with 2.5 columns visible. |
| Desktop | > 1024px | Full layout: sidebar filters always visible, property grid 3-4 cards/row, full 5-column Kanban board, side-by-side Compare (up to 4 columns). |

**Cross-cutting rule:** Per the persona data (Priya is 80% mobile, Arjun is mobile-during-the-day), the Buyer and Broker experiences are designed **mobile-first**; the Admin experience (Rakesh, desktop-always) is designed **desktop-first** and is not required to be fully feature-complete on mobile — a reduced "monitoring only" mobile view is acceptable for Admin screens, per BRD's stated web-only, no-native-app scope.

## 11. Empty / Loading / Error States

Following the principle that **words are design material** — every state below is written in the interface's voice: direct, no apology, tells the person what to do next.

### 11.1 Loading States

| Context | Pattern |
|---|---|
| Search results | Skeleton cards (matching final card shape) — never a spinner alone, which gives no sense of what's coming |
| Property detail | Skeleton for gallery + text blocks |
| Charts (Analytics) | Skeleton chart shape with axis lines, not a blank card |
| Button actions (submit, approve, book) | In-button spinner replacing the label text, button disabled during the action (per UI-REQ-07) |

### 11.2 Empty States

| Context | Heading | Body | Action |
|---|---|---|---|
| No search results | "No properties match these filters" | "Try widening your budget range or removing a filter." | `[Clear Filters]` button |
| Empty Wishlist | "Nothing saved yet" | "Properties you save will show up here." | `[Browse Properties]` button |
| No leads yet (new Broker) | "No leads yet" | "Leads appear automatically when a buyer contacts you or books a visit." | none — informational only |
| Empty Analytics (new listing) | "No activity yet" | "Once buyers start viewing this listing, you'll see numbers here." | none |
| Admin queue empty | "Nothing pending review" | "New submissions will appear here." | none |

### 11.3 Error States

| Context | Message Pattern |
|---|---|
| Form validation | Inline, field-level, specific: "Price must be greater than ₹0" — never a generic "Invalid input" |
| Booking slot no longer available (race condition, UC-ES-02) | "This slot was just booked by someone else. Here are other open times:" + refreshed slot list inline — never a dead-end error |
| Network/service failure | "Something went wrong on our end. Your changes weren't lost — try again." (paired with the relevant draft-autosave guarantee where applicable) |
| Review submission blocked (no completed booking) | "You can review a property after a completed visit." — factual, not scolding |
| 404 / unavailable shared property | "This property is no longer available." + `[Browse similar properties]` — never a bare 404 page |

## 12. Accessibility Guidelines

Target: **WCAG 2.1 Level AA** across the platform.

| ID | Requirement |
|---|---|
| A11Y-01 | Minimum contrast ratio 4.5:1 for body text, 3:1 for large text (18px+) and UI component boundaries — verified against the Section 8.1 palette in **both** themes (`--text-primary` on `--bg` passes AAA in light and AA+ in dark; `--accent-cta` is never used as a text color without a contrast check, only as a solid-fill button background with white/near-black text as appropriate per theme) |
| A11Y-02 | All interactive elements have a visible keyboard focus state (never `outline: none` without a replacement focus style) |
| A11Y-03 | Full keyboard operability: search filters, Schedule Visit picker, Lead Kanban ("Move to..." menu fallback per Section 10), and all modals/sheets are operable without a mouse |
| A11Y-04 | All form inputs have associated `<label>` elements (not placeholder-only labeling) |
| A11Y-05 | Status conveyed by color (Approved/Pending/Rejected badges, moderation flags) is always paired with text or an icon shape — never color alone |
| A11Y-06 | Images (property photos) have descriptive alt text; decorative icons are marked `aria-hidden` |
| A11Y-07 | `prefers-reduced-motion` is respected — card hover transitions, Kanban drag animations, and chart entrance animations are disabled/reduced for users who request it |
| A11Y-08 | Toast notifications and inline errors are announced to screen readers via `aria-live` regions, not visual-only |
| A11Y-09 | Charts (Analytics screens) include a text/table equivalent of the data, not visual-only representation, for screen reader users |
| A11Y-10 | Touch targets on mobile are minimum 44×44px (applies especially to Kanban "Move to..." menu items and filter chips) |
