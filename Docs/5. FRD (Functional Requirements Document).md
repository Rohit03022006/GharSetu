## 1. Purpose & How to Read This Document

The SRS states *what* the system must do (one-line FR statements, e.g., `FR-BOOK-04`). This FRD expands the significant ones into full **use-case specifications** - actor, preconditions, step-by-step main flow, alternate/exception flows, postconditions, and business rules - the level of detail a developer needs to write the actual handler function without guessing edge cases. Every use case below is traceable back to its SRS FR ID(s).

**Use Case format used throughout:**
```
UC-ID | Title
Actor: who initiates this
Preconditions: what must be true before this can run
Main Flow: numbered happy-path steps
Alternate/Exception Flows: numbered deviations and how they're handled
Postconditions: state of the system after success
Business Rules: constraints that apply regardless of flow path
Traceability: SRS FR ID(s)
```

## 2. Identity Service - Functional Requirements

### 2.1 Overview
Owns authentication, authorization, user/role records, and the Builder/Broker verification workflow. Every other service trusts this service's JWTs without a network call (shared signing secret).

### 2.2 Actors
Buyer, Builder, Broker, Admin, Guest (unauthenticated)

### 2.3 Use Cases

**UC-ID-01 | Register with Email/Phone**
- **Actor:** Guest
- **Preconditions:** Email/phone not already registered
- **Main Flow:** 1) User submits email/phone + password 2) System validates format and password strength 3) Password hashed (bcrypt) 4) User record created with default role `Buyer` 5) Verification email/SMS optionally triggered 6) JWT pair issued
- **Alternate Flows:** A1) Email/phone already exists -> HTTP 409, "Account already exists" A2) Password fails strength check -> HTTP 400 with specific rule violated
- **Postconditions:** New `Users` row exists with hashed password, role = `Buyer`
- **Business Rules:** Password minimum 8 chars, at least 1 number and 1 letter; email/phone uniqueness enforced at DB level (unique constraint), not just application check
- **Traceability:** FR-AUTH-01

**UC-ID-02 | Login via Google OAuth2**
- **Actor:** Guest
- **Preconditions:** Google account accessible to user
- **Main Flow:** 1) User clicks "Continue with Google" 2) Redirected to Google consent screen 3) Google redirects back with auth code 4) System exchanges code for Google profile (email, name) 5) System checks if email matches an existing user 6) If new, creates user with role `Buyer`; if existing, logs in 7) JWT pair issued
- **Alternate Flows:** A1) Google email matches an existing email/phone-registered account -> accounts are linked (same user record, added OAuth identifier), not duplicated A2) User denies consent -> redirect back to login screen, no error state persisted
- **Postconditions:** User authenticated; if new, `Users` row created with `auth_provider = google`
- **Business Rules:** OAuth-created accounts cannot self-select Builder/Broker role at signup (FR-USER-03 applies uniformly)
- **Traceability:** FR-AUTH-03

**UC-ID-03 | Access Protected Route with Expired Token**
- **Actor:** Any authenticated role
- **Preconditions:** User previously logged in, access token has expired
- **Main Flow:** 1) Client sends expired access token 2) Service rejects with HTTP 401 + `token_expired` code 3) Client silently calls `/auth/refresh` with refresh token 4) New access/refresh pair issued 5) Original request retried
- **Alternate Flows:** A1) Refresh token also expired/invalid -> HTTP 401 `session_expired`, client must redirect to login A2) Refresh token reused after rotation (replay attempt) -> all tokens for that user session revoked, forces re-login (security response, not silent failure)
- **Postconditions:** Either a valid new token pair, or a forced logout
- **Business Rules:** Refresh token rotation is mandatory - each use invalidates the prior token (SEC-02)
- **Traceability:** FR-AUTH-05, FR-AUTH-07, SEC-02

**UC-ID-04 | Builder/Broker Submits Verification**
- **Actor:** Builder, Broker
- **Preconditions:** User has registered with role `Builder` or `Broker`; account currently `pending_verification`
- **Main Flow:** 1) User uploads business name, RERA registration (Builder) or broker license (Broker), and contact proof 2) Documents uploaded to MinIO via Identity Service 3) Verification request enters Admin queue 4) User sees "Pending Verification" state on dashboard
- **Alternate Flows:** A1) Required document missing/unreadable file type -> rejected at upload with specific error, request not submitted
- **Postconditions:** `Verification_Status = pending_verification`, documents linked to user record
- **Business Rules:** A Builder/Broker cannot publish any listing to `live` while not `verified` (enforced in Listing Service too - see UC-LS-04)
- **Traceability:** FR-USER-03

**UC-ID-05 | Admin Approves/Rejects Verification**
- **Actor:** Admin
- **Preconditions:** At least one pending verification request exists
- **Main Flow:** 1) Admin opens verification queue 2) Reviews submitted documents 3) Approves -> `Verification_Status = verified`, `Verified_By` and `Verified_At` recorded 4) User notified
- **Alternate Flows:** A1) Admin rejects -> status = `rejected`, reason recorded, user notified and can resubmit (loops back to UC-ID-04)
- **Postconditions:** Audit record created regardless of outcome
- **Business Rules:** Every status change is logged with actor + timestamp (audit trail, non-negotiable)
- **Traceability:** FR-USER-04, FR-USER-05

### 2.4 Complete Functional Requirement Coverage (Identity Service)
`FR-AUTH-01` through `FR-AUTH-07`, `FR-USER-01` through `FR-USER-05` - see SRS Section 3.1–3.2 for the full one-line list; all are covered by the use cases above or are straightforward CRUD not requiring expanded use-case detail (e.g., FR-USER-01 admin user listing/pagination).

## 3. Listing Service - Functional Requirements

### 3.1 Overview
Source of truth for every property: creation, approval lifecycle, search, reviews, and public sharing. The highest-traffic service (every buyer, including guests, touches it).

### 3.2 Actors
Builder, Broker, Buyer, Admin, Guest

### 3.3 Use Cases

**UC-LS-01 | Create Draft Property**
- **Actor:** Builder, Broker
- **Preconditions:** User authenticated with role Builder/Broker (verification not required to draft, only to publish)
- **Main Flow:** 1) User opens "Add Property" form 2) Fills available fields (partial allowed) 3) System auto-saves every ≤30s 4) User can exit and resume anytime
- **Alternate Flows:** A1) Session expires mid-edit -> last auto-saved state preserved, user re-authenticates and resumes
- **Postconditions:** `Properties` row with `status = draft`
- **Business Rules:** No field is mandatory at draft stage except an internal working title (to distinguish drafts in the user's list)
- **Traceability:** FR-PROP-01, FR-PROP-02

**UC-LS-02 | Submit Property for Approval**
- **Actor:** Builder, Broker
- **Preconditions:** Property in `draft` status; all mandatory fields for publishing complete (title, price, area, listing type, at least 1 image, location)
- **Main Flow:** 1) User clicks "Publish" 2) System validates all mandatory fields present 3) System runs duplicate-detection check (address/lat-long + price + area similarity) 4) Status -> `pending` 5) Enters Admin moderation queue
- **Alternate Flows:** A1) Mandatory field missing -> submission blocked, specific missing fields listed A2) Duplicate detected -> still submitted, but flagged for Admin with a "possible duplicate of [property X]" indicator (advisory, not blocking)
- **Postconditions:** `status = pending`, visible in Admin queue, not yet publicly visible
- **Business Rules:** Draft -> pending is the only user-triggered transition; user cannot self-approve
- **Traceability:** FR-PROP-03, FR-PROP-06

**UC-LS-03 | Admin Approves Property**
- **Actor:** Admin
- **Preconditions:** Property in `pending` status; owning Builder/Broker account is `verified` (Identity Service)
- **Main Flow:** 1) Admin reviews listing in moderation queue 2) Checks against duplicate-flag if present 3) Approves 4) Status -> `approved` -> immediately `live` 5) Publishes `property.approved` event to Redis (consumed by Analytics Service)
- **Alternate Flows:** A1) Owning account is not verified (edge case - shouldn't reach queue, but defensively checked) -> approval blocked with error, routes admin to Identity verification queue instead
- **Postconditions:** Property appears in public search (`FR-PROP-08`), event published
- **Business Rules:** Approval is blocked at the API layer if the owner's `Verification_Status != verified`, even if somehow the listing reached the queue
- **Traceability:** FR-PROP-04, FR-USER-03 (cross-referenced)

**UC-LS-04 | Admin Rejects Property**
- **Actor:** Admin
- **Preconditions:** Property in `pending` status
- **Main Flow:** 1) Admin selects rejection reason from enum (`Spam, Duplicate, Fake, Incomplete, Policy_Violation, Other`) 2) Optional free-text note 3) Status -> `rejected` 4) Owner notified with reason
- **Alternate Flows:** none - rejection without a reason is rejected by the API itself (this is a system-enforced rule, not just a UI requirement)
- **Postconditions:** Owner can edit and resubmit (loops to UC-LS-02)
- **Business Rules:** Repeated rejections for `Fake`/`Duplicate` reasons from the same account feed a counter checked by Identity Service's verification-revocation logic
- **Traceability:** FR-PROP-05

**UC-LS-05 | Guest/Buyer Searches Properties**
- **Actor:** Guest, Buyer
- **Preconditions:** None (public endpoint)
- **Main Flow:** 1) User applies filters (city, budget, BHK, etc.) 2) System checks Redis for cached result matching the exact filter combination 3) Cache hit -> return immediately 4) Cache miss -> query PostgreSQL (indexed columns), cache result (TTL 5 min), return
- **Alternate Flows:** A1) Zero results -> return empty array with `total: 0`, not an error A2) Malformed filter (e.g., non-numeric budget) -> HTTP 400 with field-specific message
- **Postconditions:** Paginated result set returned; search event optionally logged (for authenticated buyers, feeds Discovery-History Service)
- **Business Rules:** Only `approved`/`live` properties are ever returned - enforced in the query itself (`WHERE status = 'live'`), not filtered client-side
- **Traceability:** FR-SEARCH-01 through FR-SEARCH-04, FR-PROP-08

**UC-LS-06 | Buyer Submits a Review**
- **Actor:** Buyer
- **Preconditions:** Buyer has a booking for this property; that booking's status is `Completed` (verified via Engagement Service)
- **Main Flow:** 1) Buyer submits rating (1–5) + comment 2) Listing Service calls `GET /internal/bookings/verify-completed` on Engagement Service 3) Engagement Service confirms a completed booking exists for this buyer+property 4) Review accepted, linked to that booking 5) Average rating recalculated and cached
- **Alternate Flows:** A1) No completed booking found -> HTTP 403, "Review requires a completed visit" A2) Engagement Service unreachable -> HTTP 503, review rejected (not silently accepted) - correctness prioritized over availability here, per HLD Section 2.2 A3) Buyer already reviewed this specific booking -> HTTP 409, "Already reviewed"
- **Postconditions:** New `Reviews` row linked to `booking_id`; property's cached average rating updated
- **Business Rules:** One review per booking (not per property) - a buyer with multiple completed visits over time can leave multiple honest reviews
- **Traceability:** FR-REV-01, FR-REV-02, FR-REV-05

**UC-LS-07 | Guest Views a Shared Property Link**
- **Actor:** Guest
- **Preconditions:** Property exists and is `live` (or was live at time of share - see edge case)
- **Main Flow:** 1) Guest opens shared URL 2) Listing Service returns read-only property view + Open Graph meta tags 3) Guest can view images, price, description, reviews - cannot wishlist/book/review without login
- **Alternate Flows:** A1) Property has since been unpublished/sold -> page shows "This property is no longer available" rather than a broken 404, with a link to browse similar live properties
- **Postconditions:** No state change (pure read)
- **Business Rules:** Actions beyond viewing always redirect to login, preserving the intended action to resume post-login (e.g., "wishlist this property" resumes automatically after login)
- **Traceability:** FR-SHARE-01, FR-SHARE-02, FR-SHARE-03

### 3.4 Complete Functional Requirement Coverage (Listing Service)
`FR-PROP-01` through `FR-PROP-10`, `FR-SEARCH-01` through `FR-SEARCH-04`, `FR-REV-01` through `FR-REV-05`, `FR-SHARE-01` through `FR-SHARE-03`.

## 4. Finance Service - Functional Requirements

### 4.1 Overview
Fully stateless computation service - no user data, no auth-dependent logic beyond the Admin rate-table update endpoint. Simplest service in the system by design.

### 4.2 Actors
Guest, Buyer, Admin

### 4.3 Use Cases

**UC-FS-01 | Guest/Buyer Computes EMI**
- **Actor:** Guest, Buyer
- **Preconditions:** None
- **Main Flow:** 1) User inputs price, loan amount, interest rate, tenure 2) System computes EMI via reducing-balance formula 3) Returns monthly EMI, total interest, total cost, and amortization breakdown
- **Alternate Flows:** A1) Loan amount exceeds price -> still computed (not blocked; some buyers legitimately borrow for registration/furnishing too), but UI surfaces a soft warning A2) Negative or zero inputs -> HTTP 400
- **Postconditions:** No state change - pure computation
- **Business Rules:** Computation happens client-side where possible for instant feedback; server-side endpoint exists for consistency when embedding in shared/exported views (e.g., PDF export of a property with EMI shown)
- **Traceability:** FR-FIN-01

**UC-FS-02 | Guest/Buyer Computes Stamp Duty & Registration**
- **Actor:** Guest, Buyer
- **Preconditions:** Property's state is known (from property data or manually selected)
- **Main Flow:** 1) User inputs property value + state (+ buyer category if applicable, e.g., women-buyer discount states) 2) System looks up current rate from `Finance_Rates` table for that state 3) Returns computed stamp duty and registration cost
- **Alternate Flows:** A1) State not yet configured in `Finance_Rates` -> returns a clear "rate not available for this state yet" rather than a wrong number or silent zero
- **Postconditions:** No state change
- **Business Rules:** Never fabricate a rate for an unconfigured state - an honest "unavailable" beats a wrong number for a financial estimate
- **Traceability:** FR-FIN-02, FR-FIN-06

**UC-FS-03 | Admin Updates Finance Rate Table**
- **Actor:** Admin
- **Preconditions:** Admin authenticated
- **Main Flow:** 1) Admin opens rate management screen 2) Updates a state's stamp duty %, registration %, or GST applicability rule 3) Change saved to `Finance_Rates` 4) Takes effect immediately for all subsequent calculations (no redeploy)
- **Alternate Flows:** none of note - this is a straightforward config update
- **Postconditions:** `Finance_Rates` row updated with `updated_by`, `updated_at`
- **Business Rules:** Rate changes are logged (who changed what, when) since incorrect financial estimates are a trust-critical issue
- **Traceability:** FR-FIN-06

### 4.4 Complete Functional Requirement Coverage (Finance Service)
`FR-FIN-01` through `FR-FIN-06`.

## 5. Preference Service - Functional Requirements

### 5.1 Overview
Small, focused service: what a buyer likes and wants to compare. Stores references only - resolves display data from Listing Service on read.

### 5.2 Actors
Buyer

### 5.3 Use Cases

**UC-PS-01 | Buyer Adds/Removes Wishlist Item**
- **Actor:** Buyer
- **Preconditions:** Property exists (does not need to still be `live` to remain wishlisted - see alternate flow)
- **Main Flow:** 1) Buyer clicks wishlist icon on a property 2) `property_id` reference stored against `buyer_id` 3) Icon state updates immediately (optimistic UI)
- **Alternate Flows:** A1) Property later becomes unavailable (sold/archived) -> remains in wishlist list but visually marked "no longer available," not silently removed (buyer's intent record is preserved)
- **Postconditions:** `Wishlist` row created/deleted
- **Business Rules:** Wishlist is a simple many-to-many; no cap on wishlist size (unlike Compare, which caps at 4)
- **Traceability:** FR-WISH-01

**UC-PS-02 | Buyer Compares Properties**
- **Actor:** Buyer
- **Preconditions:** Buyer has selected between 2 and 4 properties
- **Main Flow:** 1) Buyer selects properties to compare 2) Preference Service resolves each `property_id` against Listing Service (`GET /internal/properties/:id`, batched) 3) Redis-cached for 2 minutes to avoid repeated calls on the same comparison set 4) Comparison table returned
- **Alternate Flows:** A1) Buyer attempts to add a 5th property -> rejected client-side and server-side with "Maximum 4 properties" A2) One of the compared properties becomes unavailable mid-session -> still shown in the comparison with an "unavailable" badge, not silently dropped (avoids confusing the buyer about why their comparison changed)
- **Postconditions:** No persistent state unless buyer explicitly saves the comparison (out of MVP scope, noted in PRD future enhancements)
- **Business Rules:** Hard cap of 4 - enforced both client and server side
- **Traceability:** FR-WISH-02

### 5.4 Complete Functional Requirement Coverage (Preference Service)
`FR-WISH-01`, `FR-WISH-02`.

## 6. Discovery-History Service - Functional Requirements

### 6.1 Overview
Tracks what a buyer has seen and surfaces what to show them next. Receives view events from Listing Service asynchronously-adjacent (internal sync call at view time, per HLD).

### 6.2 Actors
Buyer

### 6.3 Use Cases

**UC-DH-01 | Log a Property View**
- **Actor:** Buyer (triggered by Listing Service on their behalf)
- **Preconditions:** Buyer authenticated and viewing a property detail page
- **Main Flow:** 1) Listing Service calls `POST /internal/views` on Discovery-History Service with `buyer_id` + `property_id` 2) If this property is already in the buyer's recent list, it's moved to the top (not duplicated) 3) If the list exceeds 20 entries, the oldest is trimmed
- **Alternate Flows:** A1) Discovery-History Service temporarily unreachable -> view logging fails silently (non-critical path), does not block the buyer's page load
- **Postconditions:** `Recently_Viewed` list for that buyer has ≤ 20 entries, most-recent-first
- **Business Rules:** This is a best-effort, non-blocking side effect of viewing a property - never allowed to slow down or fail the actual property view request
- **Traceability:** FR-REC-01, FR-REC-02

**UC-DH-02 | Surface Similar Properties**
- **Actor:** Buyer
- **Preconditions:** Buyer has some search/view history to derive a pattern from
- **Main Flow:** 1) Buyer views dashboard or a property detail page 2) System determines buyer's dominant pattern (most frequent city + budget band + bedroom count from recent searches) 3) Queries Listing Service for properties matching that pattern (±10% budget) 4) Excludes properties already booked or explicitly marked "not interested" by the buyer 5) Returns up to N similar properties
- **Alternate Flows:** A1) Buyer has no search history yet (new user) -> falls back to city-popular or recently-listed properties rather than an empty section
- **Postconditions:** No state change - pure read/recommendation
- **Business Rules:** V1 is rule-based, deterministic, and explainable (not a black-box model) - matches the PRD's stated V1->V2 roadmap
- **Traceability:** FR-REC-03, FR-REC-04

### 6.4 Complete Functional Requirement Coverage (Discovery-History Service)
`FR-REC-01` through `FR-REC-04`.

## 7. Engagement Service - Functional Requirements

### 7.1 Overview
The most transactionally sensitive service - owns Leads, Bookings, Availability, and Notifications together specifically so a booking action can update a lead stage and fire a notification within a single local DB transaction.

### 7.2 Actors
Buyer, Broker, Builder

### 7.3 Use Cases

**UC-ES-01 | Broker/Builder Sets Availability**
- **Actor:** Broker, Builder
- **Preconditions:** Verified account
- **Main Flow:** 1) User opens Availability Calendar 2) Marks open slots (date + time ranges) or blocks out dates 3) Slots saved as `Availability_Calendar` entries with `is_booked = false`
- **Alternate Flows:** A1) User attempts to block a date that has an existing pending booking -> system warns "N pending bookings exist on this date" before allowing the block, rather than silently orphaning those bookings
- **Postconditions:** Calendar reflects current availability, visible to buyers via `GET /availability/:brokerId`
- **Business Rules:** This calendar is the single source of truth for what a buyer can even select - buyers never see a raw date-picker with no constraints
- **Traceability:** FR-BOOK-01

**UC-ES-02 | Buyer Books a Visit**
- **Actor:** Buyer
- **Preconditions:** Target broker/builder has at least one open slot; buyer is authenticated
- **Main Flow:** 1) Buyer selects an open slot 2) `POST /bookings` 3) System validates: JWT valid -> role = Buyer -> slot exists and `is_booked = false` 4) In a single DB transaction: Booking created (`status = pending`), slot marked `is_booked = true`, Lead created or updated to stage `Interested` 5) Notification dispatched (in-app guaranteed, email/SMS best-effort)
- **Alternate Flows:** A1) Two buyers attempt to book the same slot simultaneously (race condition) -> DB-level unique constraint / row lock on the slot ensures only one succeeds; the second gets HTTP 409 "Slot no longer available" and is shown updated availability A2) Notification (email/SMS) delivery fails -> booking still succeeds; failure is logged, not surfaced as a booking error (FR-NOTIF-04)
- **Postconditions:** Booking exists in `pending` state; slot unavailable to others; Lead pipeline updated
- **Business Rules:** The atomicity of booking-creation + slot-locking + lead-update is the core reason this service isn't split further (see HLD Section 2.1)
- **Traceability:** FR-BOOK-02, FR-BOOK-05, FR-LEAD-01, FR-NOTIF-01–04

**UC-ES-03 | Buyer or Broker Reschedules a Booking**
- **Actor:** Buyer, Broker, Builder
- **Preconditions:** Booking exists in `pending` or `approved` status
- **Main Flow:** 1) Either party proposes a new slot from the same broker's availability 2) New booking record created, `Rescheduled_From` linking to the original 3) Original slot released (`is_booked = false`) 4) Other party notified
- **Alternate Flows:** A1) Proposed new slot is also unavailable (raced by someone else) -> reschedule fails, original booking remains untouched (not left in a broken intermediate state) - this is why slot-release and new-booking-creation happen in one transaction, not two separate calls
- **Postconditions:** Old booking marked `rescheduled` (terminal), new booking `pending`, calendar consistent
- **Business Rules:** A slot must never appear simultaneously double-booked or "lost" (neither party has it) - this is the single most important invariant in this service
- **Traceability:** FR-BOOK-03, FR-BOOK-04

**UC-ES-04 | Broker/Builder Moves a Lead Through the Pipeline**
- **Actor:** Broker, Builder
- **Preconditions:** Lead exists in a non-terminal stage
- **Main Flow:** 1) User drags/moves lead card to next stage on Kanban board 2) System validates the transition is sequential (`New_Lead -> Interested -> Site_Visit -> Negotiation -> Booked`) or a valid exit to `Lost` 3) Transition appended to `Lead_Stage_History` with timestamp + actor 4) Lead's current stage updated
- **Alternate Flows:** A1) User attempts to skip a stage (e.g., `New_Lead -> Booked` directly) -> HTTP 400, rejected - UI should prevent this via drag-target validation, but the API enforces it regardless of UI state
- **Postconditions:** Lead stage updated; history is append-only (never overwritten), which is what powers the Conversion Funnel chart in Analytics Service
- **Business Rules:** `Lost` is reachable from any non-terminal stage (a buyer can drop out at any point); forward stages cannot be skipped
- **Traceability:** FR-LEAD-02, FR-LEAD-03, FR-LEAD-04

### 7.4 Complete Functional Requirement Coverage (Engagement Service)
`FR-LEAD-01` through `FR-LEAD-05`, `FR-BOOK-01` through `FR-BOOK-05`, `FR-NOTIF-01` through `FR-NOTIF-04`.

## 8. Analytics Service - Functional Requirements

### 8.1 Overview
Read-only from the outside - receives all its data asynchronously via Redis Pub/Sub events from other services, never via direct writes through the gateway.

### 8.2 Actors
Builder, Broker, Admin

### 8.3 Use Cases

**UC-AS-01 | Builder Views Property/Sales Analytics**
- **Actor:** Builder, Broker
- **Preconditions:** Owns at least one property with recorded activity
- **Main Flow:** 1) User opens analytics dashboard 2) Requests chart data for a date range 3) Analytics Service reads from pre-aggregated tables (never raw event rows at request time) 4) Returns Views/Leads/Conversion-funnel/Revenue chart data
- **Alternate Flows:** A1) No activity yet for a new listing -> charts render with an empty/zero state and a "check back once your listing gets traffic" message rather than an error
- **Postconditions:** No state change - pure read
- **Business Rules:** All chart-backing data must already be aggregated by a scheduled job before this endpoint is called - this endpoint must never trigger an on-demand aggregation over raw data (would violate NFR performance targets under load)
- **Traceability:** FR-ANLY-01, FR-ANLY-02

**UC-AS-02 | Aggregation Job Processes Events**
- **Actor:** System (scheduled job, no human actor)
- **Preconditions:** Events have been published to Redis by Listing/Engagement Services since the last run
- **Main Flow:** 1) Scheduled job (cron) runs 2) Consumes queued/streamed events (`property.approved`, `booking.completed`, `lead.stage_changed`, `property.viewed`) 3) Updates time-bucketed aggregation tables 4) Marks events processed
- **Alternate Flows:** A1) Job fails partway through -> must be safely re-runnable without double-counting (idempotent aggregation, e.g., using event IDs to dedupe) - this is a hard requirement, not a nice-to-have, because double-counted revenue/views would undermine the entire trust premise of "give builders numbers they can act on" from the BRD
- **Postconditions:** Aggregation tables reflect all processed events
- **Business Rules:** Idempotency is mandatory for this job
- **Traceability:** FR-ANLY-04

**UC-AS-03 | Admin Views Platform Analytics Dashboard**
- **Actor:** Admin
- **Preconditions:** None (always available, may show zero-state on a fresh deployment)
- **Main Flow:** 1) Admin opens platform dashboard 2) Selects a date range 3) System returns DAU/MAU, monthly revenue, top cities, top builders, booking trend, growth rates - all from pre-aggregated platform-wide tables
- **Alternate Flows:** none of particular note beyond standard empty-state handling
- **Postconditions:** No state change
- **Business Rules:** Same pre-aggregation principle as UC-AS-01, at platform scope instead of per-property
- **Traceability:** FR-ANLY-03

### 8.4 Complete Functional Requirement Coverage (Analytics Service)
`FR-ANLY-01` through `FR-ANLY-04`.

| All Services | Identity | (JWT validation) | No network call - local validation via shared secret |

## 10. Traceability Note

Every UC-ID in this document maps 1:1 or 1:many to SRS FR-IDs, which in turn map to PRD feature sections, which map to BRD business requirements. This chain (`BR-xx -> PRD §x.x -> FR-xxx-xx -> UC-xx-xx`) is what makes each requirement defensible end-to-end - a reviewer can ask "why does this exist" at any layer and trace it back to a business reason, not just an engineering preference.
