## 1. Introduction

### 1.1 Purpose
This SRS translates the PRD's feature descriptions into implementation-ready specifications: numbered functional requirements, non-functional requirements, system behavior (state machines), concrete API contracts, and security requirements — everything a developer needs to start building without re-deriving decisions from the PRD prose.

### 1.2 Cost Principle (applies to this entire document)
**Every tool, library, and service referenced in this SRS is free and/or open-source**, unless explicitly marked otherwise. Where a typical SaaS product would use a paid vendor (email delivery, SMS, hosting, monitoring), this document specifies the open-source or free-tier equivalent instead. This is a hard constraint carried over from the PRD/BRD, not just a preference.

### 1.3 Intended Audience
Developers implementing the system (primary), and technical reviewers (interviewers, hackathon judges) evaluating implementation depth.

## 2. System Overview

Four actors — **Admin, Builder, Broker, Buyer** — interact through an **API Gateway (Nginx)** that routes to **7 independently deployable microservices**, each owning its own PostgreSQL schema/database and communicating via synchronous REST calls (critical-path reads) and asynchronous events (Redis Pub/Sub, no additional broker needed since Redis is already in the stack for caching). This replaces the earlier monolithic design — the service boundaries below are drawn along domains that are either fully self-contained or tightly operationally coupled (to avoid distributed-transaction problems within a single business flow).

### 2.1 Service Boundaries

| # | Service Name | Owns | Modules Covered |
|---|---|---|---|
| 1 | **Identity Service** | Users, Roles, Permissions, Verification | Auth, User & Role Management |
| 2 | **Listing Service** | Properties, Property_Images, Reviews, Amenities, Cities/Locations | Property Management, Search & Discovery, Reviews & Ratings, Property Sharing |
| 3 | **Finance Service** | Finance_Rates (config only, no user data) | Finance Suite (EMI, Stamp Duty, GST, Registration, Maintenance) |
| 4 | **Preference Service** | Wishlist, Compare_History | Wishlist & Compare |
| 5 | **Discovery-History Service** | Recently_Viewed, Search_History, Similar-Properties matching | Recently Viewed & Similar Properties |
| 6 | **Engagement Service** | Leads, Lead_Stage_History, Bookings, Availability_Calendar, Notifications | Lead Management, Booking & Availability, Notifications |
| 7 | **Analytics Service** | Property_Views (event log), pre-aggregated metrics tables | Analytics (builder-facing + admin platform dashboard) |

**Why this split works:** Services 6 (Engagement) keeps Booking + Lead + Notifications together deliberately — a booking state change must atomically update the lead stage and fire a notification, and keeping these three in one service means that stays a local DB transaction instead of a distributed one. Same logic applies to Service 2 grouping Property + Reviews + Search together — search reads property status directly, no cross-service call needed for the platform's highest-traffic path.

### 2.2 Cross-Service Dependencies (called out explicitly, not hidden)

| Dependency | Caller → Callee | Type | Handling |
|---|---|---|---|
| Review eligibility check | Listing Service → Engagement Service | Sync (REST) | Listing Service calls `GET /internal/bookings/verify-completed?buyer_id&property_id` on review submission. If Engagement Service is unreachable, the review submission fails gracefully (HTTP 503) rather than allowing an unverified review through — correctness over availability here. |
| Property data for Wishlist/Compare display | Preference Service → Listing Service | Sync (REST), cached | Preference Service stores only `property_id` references; fetches display data from Listing Service on read, with a short Redis cache (TTL 2 min) to avoid hammering Listing Service. |
| Property data for Recently Viewed/Similar | Discovery-History Service → Listing Service | Sync (REST), cached | Same pattern as above. |
| Property data for Booking | Engagement Service → Listing Service | Sync (REST) at booking-creation time only | Engagement Service snapshots price/builder info into the Booking record at creation time (denormalized copy) — so historical bookings remain accurate even if the listing changes later, and Engagement doesn't need a live call on every booking read. |
| Event stream for Analytics | Listing Service, Engagement Service → Analytics Service | Async (Redis Pub/Sub) | Services publish domain events (`property.approved`, `booking.completed`, `lead.stage_changed`, `property.viewed`) to Redis channels; Analytics Service subscribes and updates its own aggregation tables. Analytics never queries other services' databases directly. |
| User identity/role validation | All services → Identity Service | Sync (JWT, not a network call) | JWT is validated locally by each service (shared signing secret) — this is the one dependency that does NOT require a network call per request, keeping the gateway fast. Identity Service is only called directly for account-level actions (verification status, profile updates). |

### 2.3 Inter-Service Communication Stack (kept free/OSS per Section 1.2)

- **Synchronous:** REST over HTTP/JSON between services (simple, matches team's existing REST skillset — gRPC considered but adds a learning-curve cost not justified at this scale)
- **Asynchronous:** Redis Pub/Sub for event broadcast (reuses the Redis instance already required for caching — avoids introducing RabbitMQ/Kafka as a new piece of infra for a project this size)
- **API Gateway:** Nginx, doing path-based routing (`/api/v1/auth/* → Identity Service`, `/api/v1/properties/* → Listing Service`, etc.) plus TLS termination and rate limiting — free, and already in the stack as a reverse proxy
- **Service Discovery:** Kubernetes-native (ClusterIP Services + internal DNS) — no separate service-registry tool (e.g., Consul) needed once deployed on K8s, which fits directly into the Helm/Kustomize/ArgoCD GitOps workflow already in progress
- **Each service:** own Docker image, own Helm chart (or shared chart with per-service values.yaml), independently deployable via the ArgoCD GitOps pipeline

```
                              Client (React SPA)
                                      │
                            API Gateway (Nginx)
                                      │
        ┌───────────┬───────────┬────┴────┬───────────┬───────────┬───────────┐
        │           │           │         │           │           │           │
    Identity     Listing     Finance   Preference  Discovery-  Engagement  Analytics
    Service      Service     Service    Service    History     Service     Service
        │           │           │         │        Service        │           │
        │           │           │         │           │           │           │
     Postgres    Postgres   Postgres   Postgres   Postgres    Postgres    Postgres
     (identity)  (listing)  (finance)  (prefs)   (discovery) (engagement) (analytics)
        │           │                     │           │           │           │
        └───────────┴─────────────────────┴───────────┴───────────┘           │
                                      │                                        │
                              Redis (Cache + Pub/Sub event bus) ───────────────┘
                                      │
                        Shared Object Storage (MinIO — self-hosted, S3-compatible)
                        used by Listing Service for images, Identity Service
                        for verification documents
```

**Note on database-per-service:** Each service gets its own PostgreSQL database (not just schema) for genuine deployment independence — this is the textbook microservices pattern, and it's what makes each service's Helm release truly independent (a schema migration in Listing Service can never lock a table Engagement Service depends on, because there is no shared table).

## 3. Functional Requirements

Each FR includes: description, inputs, outputs, and business rule. FR IDs are grouped by module for traceability back to the PRD.

### 3.1 Authentication & Authorization (FR-AUTH)

| ID | Requirement |
|---|---|
| FR-AUTH-01 | System shall allow user registration via email/phone with password (hashed, never stored plaintext). |
| FR-AUTH-02 | System shall allow login via email/phone + password, issuing a JWT access token (short TTL, e.g., 15 min) and a refresh token (long TTL, e.g., 7 days). |
| FR-AUTH-03 | System shall support OAuth2 login via Google; first-time Google login creates a user with default role `Buyer`. |
| FR-AUTH-04 | System shall embed `user_id` and `role` as claims in the JWT payload. |
| FR-AUTH-05 | System shall reject any request to a protected route with a missing, expired, or invalid JWT (HTTP 401). |
| FR-AUTH-06 | System shall reject any request where the authenticated role lacks permission for the action (HTTP 403), enforced server-side regardless of frontend UI state. |
| FR-AUTH-07 | System shall support refresh-token rotation: each use of a refresh token invalidates the old one and issues a new pair. |

### 3.2 User & Role Management (FR-USER)

| ID | Requirement |
|---|---|
| FR-USER-01 | System shall allow Admin to view, filter, and paginate all user accounts by role and status. |
| FR-USER-02 | System shall allow Admin to suspend or reactivate any Builder/Broker/Buyer account. |
| FR-USER-03 | New Builder/Broker accounts shall default to `Verification_Status = Pending` and cannot publish live listings until `Verified`. |
| FR-USER-04 | System shall allow Admin to approve or reject verification requests, recording `Verified_By` and `Verified_At`. |
| FR-USER-05 | System shall log every verification status change to an audit table (who, when, previous → new status). |

### 3.3 Property Management (FR-PROP)

| ID | Requirement |
|---|---|
| FR-PROP-01 | System shall allow Builder/Broker to create a property listing with status `draft` (partial data allowed). |
| FR-PROP-02 | System shall auto-save draft edits at a maximum interval of 30 seconds while the form is open. |
| FR-PROP-03 | System shall allow the owner to submit a draft for review, transitioning status `draft → pending`. |
| FR-PROP-04 | System shall allow only Admin to transition a property from `pending → approved` or `pending → rejected`. |
| FR-PROP-05 | A rejection action shall require a `Rejection_Reason` from a fixed enum: `Spam, Duplicate, Fake, Incomplete, Policy_Violation, Other`. |
| FR-PROP-06 | System shall run duplicate-detection (address/lat-long + price + area similarity match) at submission time and flag potential duplicates for admin review — this is advisory, not a hard block. |
| FR-PROP-07 | System shall support `Listing_Type` of `Sale` or `Rent`; Rent listings require additional fields (`Monthly_Rent`, `Security_Deposit`, `Lease_Duration`, `Furnishing_Status`). |
| FR-PROP-08 | Only `approved` (and subsequently `live`) properties shall appear in public search results. |
| FR-PROP-09 | System shall allow the owning Builder/Broker or Admin to edit/delete a property; all other roles shall be denied (403). |
| FR-PROP-10 | System shall support property status transitions to `sold`, `rented`, or `archived` post-booking completion. |

### 3.4 Search & Discovery (FR-SEARCH)

| ID | Requirement |
|---|---|
| FR-SEARCH-01 | System shall support filtering by city, budget range, bedrooms, bathrooms, property type, builder, construction status, parking, area, furnishing, and proximity-to-metro flag. |
| FR-SEARCH-02 | System shall return paginated results (default page size 20) with total match count. |
| FR-SEARCH-03 | System shall cache search results in Redis, keyed by the normalized filter combination, with a TTL of 5 minutes. |
| FR-SEARCH-04 | System shall invalidate relevant cached search keys when a property's status or searchable fields change. |

### 3.5 Finance Suite (FR-FIN)

| ID | Requirement |
|---|---|
| FR-FIN-01 | System shall compute EMI given price, loan amount, interest rate, and tenure using the standard reducing-balance EMI formula. |
| FR-FIN-02 | System shall compute registration cost and stamp duty using a state-wise configurable rate table (`Finance_Rates`), not hardcoded values. |
| FR-FIN-03 | System shall compute GST only for `Under_Construction` properties; `Ready_to_Move` properties shall show GST as not applicable. |
| FR-FIN-04 | System shall compute an estimated maintenance cost range from area, property type, and city-tier lookup values. |
| FR-FIN-05 | For `Listing_Type = Rent`, the Finance Suite shall display a Rent Affordability view instead of EMI/stamp-duty/registration. |
| FR-FIN-06 | Admin shall be able to update `Finance_Rates` values without a code deployment (data-driven, via an admin-only API/UI). |

### 3.6 Wishlist & Compare (FR-WISH)

| ID | Requirement |
|---|---|
| FR-WISH-01 | System shall allow a Buyer to add/remove a property to/from their wishlist (many-to-many). |
| FR-WISH-02 | System shall allow a Buyer to select up to 4 properties for side-by-side comparison. |

### 3.7 Recently Viewed & Similar Properties (FR-REC)

| ID | Requirement |
|---|---|
| FR-REC-01 | System shall log each property view against the viewing buyer, capped at the 20 most recent (older entries trimmed). |
| FR-REC-02 | Re-viewing an already-logged property shall move it to the top rather than duplicate the entry. |
| FR-REC-03 | System shall surface "Similar Properties" using rule-based matching (same city + budget within ±10% + same bedroom count as the buyer's dominant search pattern) in V1. |
| FR-REC-04 | Similar Properties shall exclude properties the buyer has already booked or explicitly rejected. |

### 3.8 Reviews & Ratings (FR-REV)

| ID | Requirement |
|---|---|
| FR-REV-01 | System shall allow a Buyer to submit a rating (1–5) and comment for a property, only if they have a `Booking` with status `Completed` for that property. |
| FR-REV-02 | System shall allow one review per buyer per completed booking (not per property, to allow multiple genuine visits over time to each yield a review). |
| FR-REV-03 | System shall allow the property's Builder/Broker to submit exactly one reply per review. |
| FR-REV-04 | System shall allow Admin to moderate (hide/remove) a review; removed reviews shall be excluded from the average rating computation. |
| FR-REV-05 | System shall recompute and cache a property's average rating on new review submission (not on every page read). |

### 3.9 Lead Management (FR-LEAD)

| ID | Requirement |
|---|---|
| FR-LEAD-01 | System shall auto-create a Lead record when a Buyer submits a contact request or visit booking for a property. |
| FR-LEAD-02 | Lead stage shall follow a strict state machine: `New_Lead → Interested → Site_Visit → Negotiation → Booked`, with `Lost` reachable from any stage. |
| FR-LEAD-03 | Direct transitions that skip intermediate stages (e.g., `New_Lead → Booked`) shall be rejected by the API (HTTP 400). |
| FR-LEAD-04 | Every stage transition shall be appended to `Lead_Stage_History` with timestamp and the acting Broker/Builder's user ID (append-only, never overwritten). |
| FR-LEAD-05 | System shall allow filtering/sorting leads by stage, property, date range, and assigned broker. |

### 3.10 Booking & Availability (FR-BOOK)

| ID | Requirement |
|---|---|
| FR-BOOK-01 | System shall allow Builder/Broker to define an Availability Calendar (open slots, blocked dates). |
| FR-BOOK-02 | Buyer booking requests shall only be accepted for date/time slots present in the target Builder/Broker's availability. |
| FR-BOOK-03 | System shall support booking status transitions: `Pending → Approved → Completed`, and `Pending/Approved → Cancelled` or `→ Rescheduled`. |
| FR-BOOK-04 | A reschedule action shall create a new booking record linked via `Rescheduled_From`, and release the original slot back to availability. |
| FR-BOOK-05 | System shall trigger notifications (in-app + email + SMS) on booking creation, cancellation, and reschedule. |

### 3.11 Notifications (FR-NOTIF)

| ID | Requirement |
|---|---|
| FR-NOTIF-01 | System shall persist every notification to an in-app `Notifications` table as the guaranteed delivery channel. |
| FR-NOTIF-02 | System shall attempt email delivery via a self-hosted SMTP/OSS transactional mailer (see Section 8) as a best-effort secondary channel. |
| FR-NOTIF-03 | System shall attempt SMS delivery via an OSS/self-hosted or free-tier gateway (see Section 8) as a best-effort secondary channel. |
| FR-NOTIF-04 | Failure of email/SMS delivery shall be logged but shall never block or fail the primary action (e.g., a booking must still succeed even if the SMTP send fails). |

### 3.12 Analytics (FR-ANLY)

| ID | Requirement |
|---|---|
| FR-ANLY-01 | System shall log property view/click events to an append-only event table. |
| FR-ANLY-02 | System shall expose pre-aggregated, time-bucketed endpoints for Builder-facing charts (views, leads, conversion funnel, revenue) — never computing charts from raw event rows at request time. |
| FR-ANLY-03 | System shall expose pre-aggregated platform-wide metrics for Admin (DAU/MAU, monthly revenue, top cities, top builders, booking trend, growth rates). |
| FR-ANLY-04 | Aggregation jobs shall run on a scheduled basis (cron or equivalent), not synchronously on every dashboard load. |

### 3.13 Property Sharing (FR-SHARE)

| ID | Requirement |
|---|---|
| FR-SHARE-01 | System shall expose a public, unauthenticated read-only endpoint for viewing a single property by shareable link. |
| FR-SHARE-02 | Shared property pages shall render Open Graph meta tags (image, title, price) for social/WhatsApp preview rendering. |
| FR-SHARE-03 | Actions beyond viewing (wishlist, booking, review) shall require authentication even when accessed via a shared link. |

## 4. Non-Functional Requirements

| ID | Category | Requirement |
|---|---|---|
| NFR-01 | Performance | Cached search responses shall return in < 200ms (server-side, excluding client network latency). |
| NFR-02 | Performance | Uncached (cold) search queries shall return in < 800ms under expected data volumes (up to ~50k properties). |
| NFR-03 | Scalability | Each microservice shall be stateless (no in-memory session state) so any service can scale horizontally/independently behind the API Gateway, without scaling the others. |
| NFR-04 | Availability | The system shall target 99%+ uptime for the deployed demo, verified via health-check endpoints. |
| NFR-05 | Security | All passwords shall be hashed with bcrypt (or Argon2) — never stored or logged in plaintext. |
| NFR-06 | Security | All API inputs shall be validated server-side (Zod schemas), regardless of client-side validation. |
| NFR-07 | Security | Public-facing endpoints (search, share links) shall be rate-limited to prevent scraping/abuse. |
| NFR-08 | Maintainability | Configuration values that change without a code change (finance rates, feature flags) shall live in the database or environment config, not hardcoded. |
| NFR-09 | Observability | All API requests shall be logged with request ID, latency, and status code; error rates and latency shall be visible on a Grafana dashboard. |
| NFR-10 | Portability | The entire 7-service stack shall run locally via a single `docker-compose up` (each service + its own DB as a container) for local dev, and via Helm charts on a local K8s cluster (e.g., Minikube/KillerCoda) for deployment-realistic testing — with no paid external dependency required to boot either way. |
| NFR-14 | Independent Deployability | Each service shall be deployable, restartable, and rollback-able independently via its own ArgoCD Application — a bad deploy of one service (e.g., Analytics) must not require redeploying or restarting unrelated services. |
| NFR-11 | Data Integrity | All foreign-key relationships (Users↔Properties, Bookings↔Properties, etc.) shall be enforced at the database level, not just application level. |
| NFR-12 | Usability | The UI shall be responsive across desktop, tablet, and mobile breakpoints (no separate mobile app required for MVP). |
| NFR-13 | Cost | No paid third-party SaaS dependency shall be required for the system to function end-to-end in development or the portfolio-demo deployment (see Section 8 for the OSS tool mapping). |

## 5. System Behavior (State Machines & Key Flows)

### 5.1 Property Status State Machine

```
draft ──(submit)──▶ pending ──(admin approve)──▶ approved ──▶ live ──▶ sold / rented / archived
                       │
                       └──(admin reject, reason required)──▶ rejected ──(owner edits)──▶ pending
```
**Rule:** Only Admin can move `pending → approved/rejected`. Only the listing owner (or Admin) can move `draft → pending` or edit a `rejected` listing back into the queue.

### 5.2 Booking Status State Machine

```
pending ──(builder/broker approve)──▶ approved ──(visit occurs)──▶ completed
   │                                     │
   ├──(either party cancels)──▶ cancelled
   │                                     │
   └──(either party reschedules)──▶ rescheduled ──▶ (new booking record created, linked via Rescheduled_From)
```
**Rule:** A cancelled or completed booking is terminal — no further transitions. A rescheduled booking's original slot is released back to the Availability Calendar atomically with the new booking's creation (single DB transaction — must not allow a state where the slot is double-booked or lost).

### 5.3 Lead Pipeline State Machine

```
New_Lead ──▶ Interested ──▶ Site_Visit ──▶ Negotiation ──▶ Booked
   │             │              │               │
   └─────────────┴──────────────┴───────────────┴──▶ Lost (reachable from any non-terminal stage)
```
**Rule:** Forward transitions must be sequential (no stage-skipping) except the `Lost` exit, which is reachable from any stage. `New_Lead → Interested` is system-automated on first buyer action (visit booking); all further transitions are manual broker/builder actions.

### 5.4 User Verification State Machine

```
pending_verification ──(admin approves, docs valid)──▶ verified
        │
        └──(admin rejects)──▶ rejected ──(user resubmits)──▶ pending_verification

verified ──(admin revokes, e.g. repeated moderation violations)──▶ pending_verification
```
**Rule:** A Builder/Broker account cannot have any listing reach `live` status while not in `verified` state — this is enforced at the API layer on every property status transition, not just at listing creation.

### 5.5 Key Use Case — Buyer Books a Visit (Sequence)

```
1. Buyer views property detail page
2. Buyer clicks "Schedule Visit" → frontend requests Broker/Builder's availability calendar
3. Buyer selects an open date/time slot
4. POST /api/bookings { property_id, date, time }
5. API validates: JWT valid → role = Buyer → slot exists in target's availability → slot not already booked
6. Booking created with status = "pending"; slot marked unavailable in the same DB transaction
7. Lead auto-created/updated (FR-LEAD-01) to stage "Interested"
8. Notification dispatched: in-app (guaranteed) + email/SMS (best-effort)
9. Builder/Broker approves/rejects from their dashboard → status updates → Buyer notified
```

## 6. API Specification

All client-facing calls go through the **API Gateway** at base path `/api/v1`, which routes by path prefix to the owning service (shown in the **Service** column below). All protected routes require `Authorization: Bearer <JWT>` — the JWT is validated independently by whichever service receives the request (shared signing secret, no round-trip to Identity Service needed). Response format is JSON throughout; errors follow `{ "error": { "code": "...", "message": "..." } }`. Endpoints marked **Internal** are service-to-service only, not exposed through the gateway.

### 6.1 Authentication — *Identity Service*

| Method | Endpoint | Auth | Description |
|---|---|---|---|
| POST | `/auth/register` | Public | Register with email/phone + password |
| POST | `/auth/login` | Public | Login, returns access + refresh token |
| POST | `/auth/google` | Public | OAuth2 Google login/signup |
| POST | `/auth/refresh` | Public (refresh token) | Rotate refresh token, issue new access token |
| POST | `/auth/logout` | Authenticated | Invalidate refresh token |
| GET | `/admin/verifications` | Admin | List pending verification requests |
| POST | `/admin/verifications/:userId/approve` | Admin | Mark user verified |
| POST | `/admin/verifications/:userId/reject` | Admin | Mark user rejected |

### 6.2 Properties, Search & Reviews — *Listing Service*

| Method | Endpoint | Auth | Description |
|---|---|---|---|
| GET | `/properties` | Public | Search/filter live properties (query params per FR-SEARCH-01) |
| GET | `/properties/:id` | Public | Get property detail |
| POST | `/properties` | Builder/Broker | Create property (status defaults to `draft`) |
| PATCH | `/properties/:id` | Owner or Admin | Update property fields |
| POST | `/properties/:id/submit` | Owner | Transition `draft → pending` |
| POST | `/properties/:id/approve` | Admin | Transition `pending → approved`; publishes `property.approved` event |
| POST | `/properties/:id/reject` | Admin | Transition `pending → rejected`, body requires `reason` |
| DELETE | `/properties/:id` | Owner or Admin | Delete property |
| GET | `/properties/:id/share` | Public | Public read-only view with OG meta tags |
| POST | `/properties/:id/reviews` | Buyer | Submit review — calls Engagement Service (Internal API, 6.6) to verify a completed booking exists before accepting |
| POST | `/reviews/:id/reply` | Owning Builder/Broker | Reply to a review |
| PATCH | `/reviews/:id/moderate` | Admin | Hide/remove a review |
| GET | `/properties/:id/reviews` | Public | List reviews for a property |
| GET | `/admin/moderation/queue` | Admin | List pending property approvals (with duplicate-flag indicators) |
| GET | `/internal/properties/:id` | **Internal** | Bulk/lightweight property data for Preference, Discovery-History, and Engagement Services to resolve display info |

| Method | Endpoint | Auth | Description |
|---|---|---|---|
| POST | `/finance/emi` | Public | Compute EMI from inputs |
| POST | `/finance/stamp-duty` | Public | Compute stamp duty (state-aware) |
| POST | `/finance/gst` | Public | Compute GST (construction-status-aware) |
| POST | `/finance/registration` | Public | Compute registration cost |
| POST | `/finance/maintenance` | Public | Estimate maintenance cost range |
| PUT | `/admin/finance-rates` | Admin | Update state-wise rate table |

*Fully stateless — no dependency on any other service, which makes this the simplest service to build, test, and deploy first.*

### 6.4 Wishlist & Compare — *Preference Service*

| Method | Endpoint | Auth | Description |
|---|---|---|---|
| POST | `/wishlist/:propertyId` | Buyer | Add to wishlist (stores `property_id` reference only) |
| DELETE | `/wishlist/:propertyId` | Buyer | Remove from wishlist |

| POST | `/compare` | Buyer | Submit up to 4 property IDs, returns comparison data (same resolution pattern as above) |

### 6.5 Recently Viewed & Similar Properties — *Discovery-History Service*

| Method | Endpoint | Auth | Description |
|---|---|---|---|

### 6.6 Leads, Bookings & Notifications — *Engagement Service*

| Method | Endpoint | Auth | Description |
|---|---|---|---|
| GET | `/availability/:brokerId` | Buyer | Fetch open slots for a broker/builder |
| POST | `/bookings` | Buyer | Create booking request; snapshots property price/builder info from Listing Service at creation time |
| PATCH | `/bookings/:id/approve` | Broker/Builder | Approve pending booking |
| PATCH | `/bookings/:id/cancel` | Buyer or Broker/Builder | Cancel booking |
| PATCH | `/bookings/:id/reschedule` | Buyer or Broker/Builder | Reschedule to a new slot |
| GET | `/bookings` | Authenticated | List own bookings (role-scoped) |
| GET | `/internal/bookings/verify-completed` | **Internal** | Called by Listing Service before accepting a review submission — returns whether a `Completed` booking exists for the given buyer + property |
| GET | `/leads` | Broker/Builder | List leads (filterable by stage/property/date) |
| PATCH | `/leads/:id/stage` | Broker/Builder | Move lead to next valid stage (validated against state machine) |
| GET | `/notifications` | Authenticated | List own in-app notifications |

*This service owns the tightest transactional coupling in the system (Booking ↔ Lead ↔ Notification) — kept as one service specifically so those updates stay a single local DB transaction instead of a distributed one (see Section 2.2).*

### 6.7 Analytics — *Analytics Service*

| Method | Endpoint | Auth | Description |
|---|---|---|---|
| GET | `/analytics/property/:id` | Owner or Admin | Property-level metrics + chart data |
| GET | `/analytics/builder/:id/sales` | Owner or Admin | Views/Leads/Conversion/Revenue charts |

## 7. Security Requirements

| ID | Requirement |
|---|---|
| SEC-01 | Passwords hashed with bcrypt (cost factor ≥ 10) or Argon2id — no reversible encryption of passwords. |
| SEC-02 | JWT access tokens short-lived (≤ 15 min); refresh tokens rotated on use and revocable server-side (stored hash in DB, not just trusted client-side). |
| SEC-03 | RBAC enforced via middleware on every route — role checks never left to the frontend alone. |
| SEC-04 | All write endpoints validate input against a strict schema (Zod) — reject unknown fields and out-of-range values. |
| SEC-05 | Rate limiting on public endpoints (search, share links, login) to mitigate scraping and brute-force attempts — implemented via an OSS solution (e.g., `express-rate-limit` backed by Redis), not a paid WAF service. |
| SEC-06 | File uploads (property images, verification documents) validated for MIME type and size before processing; documents/images never executed or served as executable content. |
| SEC-07 | SQL access exclusively through Prisma's parameterized queries — no raw string-concatenated SQL, preventing injection. |
| SEC-08 | Sensitive fields (verification documents, contact info) access-restricted by role — a Buyer's phone number is not exposed to another Buyer, only to the Broker/Builder they've engaged with. |
| SEC-09 | All traffic served over HTTPS in any deployed environment (TLS via Let's Encrypt — free, automated, no paid certificate needed). |
| SEC-10 | Audit logging for sensitive admin actions: verification changes, property rejections, review moderation, account suspensions — each recorded with actor, timestamp, and action. |
| SEC-11 | CORS configured to allow only known frontend origins in production, not wildcard `*`. |
| SEC-12 | Secrets (DB credentials, JWT signing key) loaded from environment variables / `.env`, never committed to source control. |

| CDN | Nginx caching layer in front of MinIO | Free; a full CDN (Cloudflare) can be added later, but isn't required to function |
| Maps | Leaflet.js + OpenStreetMap + Overpass API + Nominatim | Fully open-source and free (unlike Google Maps API, which is paid beyond a quota) |
